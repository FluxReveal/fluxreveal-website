    LLD – Low Level Design

    Detaljert design for utviklere og for den som skal drifte eller videreutvikle løsningen: filer, dataformater, API, regelmotor, statuser og flyt.

    ⏱ Ca. 19 min lesetid

    Arkitekturen er Thomas sitt tekniske valg. Regelavklaringene er forslag som vi tar på sameiemøtet (se HLD og Hva må godkjennes?). Detaljdesignet på denne siden – filnavn, feltnavn, endepunkter, feilkoder, CSV-oppsett og detaljer i nattlig jobb – er assistentens utdyping og kan justeres ved bygging. Felter som hører til en avklaring, er merket med nummeret (f.eks. Å1).

    Innlogging, økter og PWA

    Thomas har valgt egen innlogging med e-post og passord i Workeren, i stedet for Cloudflare Access (som har maks 30 dagers økter og engangskoder på e-post som ikke kan lagres på mobilen). Se HLD: innlogging og økter og Hva må godkjennes?

    Innloggingsskjema laget for passordhåndtering

    Skjemaet er en vanlig <form> med riktige autocomplete-verdier. Da kjenner iCloud-nøkkelring, Google Passordmanager og andre passordhåndterere igjen feltene, tilbyr å lagre passordet og fyller det inn med Face ID eller fingeravtrykk.

    • autocomplete="new-password" på «velg passord» gjør at mobilen foreslår et sterkt passord og lagrer det.
    • E-post sammenlignes uten forskjell på store og små bokstaver (lagres med små bokstaver).

    Økt-cookie

    EgenskapVerdiHvorfor
    Navn__Host-ht14_okt__Host--prefikset krever Secure, Path=/ og ingen Domain.
    Verdi256 bit tilfeldig økt-nøkkel (base64url)Bare en hash av nøkkelen lagres på serveren.
    HttpOnlyjaJavaScript på siden kan ikke lese den.
    SecurejaSendes bare over HTTPS.
    SameSiteLaxSendes med når man åpner Badehusappen (også fra Hjem-skjermen eller en lenke), men ikke med skjema eller kall fra andre nettsider.
    Max-Age31536000 (365 dager)Man holder seg innlogget i ca. ett år.
    FornyingGlidendeNår økten brukes og er eldre enn ett døgn siden sist fornyet, settes ny utløpstid (nå + 365 dager) og cookien sendes på nytt. Maks én KV-skriving per økt per døgn.

    Hvorfor det virker: sidene og /api/ ligger på samme adresse (https://badehusappen.fluxreveal.workers.dev), så cookien er en vanlig førsteparts-cookie og Safari på iPhone sender den uten problemer. workers.dev står på Public Suffix List, så cookien deles ikke med andre workers.dev-adresser. Frontend kaller med relative adresser (fetch("/api/me")), og nettleserens standard credentials: "same-origin" holder.

    Hvorfor Lax og ikke Strict: Når man åpner en Hjem-skjerm-app på iPhone eller følger lenken fra fluxreveal.com/HT14/, kan første forespørsel regnes som en navigasjon fra et annet sted. En Strict-cookie blir da ikke sendt med den første forespørselen, mens Lax blir det. Siden Badehusappen sjekker innloggingen med GET /api/me etter at siden er lastet, ville Strict sannsynligvis også gått, men Lax er det trygge valget. CSRF-vernet ivaretas av Lax (ingen cookie på POST fra andre nettsider) pluss Origin-sjekken i Workeren.

    Hjem-skjerm på iPhone: En Hjem-skjerm-app har sine egne cookies, adskilt fra Safari. Fra iOS 17.2 kopieres Safari-cookiene inn når man trykker «Legg til på Hjem-skjerm», så den som er logget inn i Safari, er også logget inn i appen. Ellers logger man inn én gang i appen; passordet fylles inn automatisk.

    Øktliste (Workers KV)

    // KV-nøkkel: sess:<sha256(økt-nøkkel + pepper)>
{
  "userId": "u-per-hansen",
  "createdAt": "2027-04-02T19:10:00+02:00",
  "lastSeenAt": "2027-07-09T08:01:12+02:00",
  "expiresAt": "2028-07-08T08:01:12+02:00",
  "device": "iPhone · Safari (Hjem-skjerm)"   // grovt, fra User-Agent
}
// KV-nøkkel: user-sess:u-per-hansen  → liste over økt-hasher (for «logg ut alle»)
// KV-nøkkel: fail:<e-post> og fail-ip:<ip>  → teller for feil forsøk (med TTL)
    • Logg ut (POST /api/logout): sletter økten i KV og sender en utløpt cookie.
    • Admin logger ut en mistet mobil: velger økten i listen (enhet, sist brukt) og sletter den. Neste kall fra den mobilen får 401.
    • Admin logger ut alle økter for en bruker: alle hasher i user-sess:<id> slettes. Skjer også automatisk ved passordbytte og når en bruker deaktiveres.
    • Økter som har gått ut, ryddes av KV selv (TTL lik utløpstiden).

    HvaForslag i detaljdesign

    Mobil-først kalender

    • Ukevisning er standard (mandag–søndag som rader på mobil). Sveip eller piler for neste og forrige uke. Månedsvisning kan velges, og valget huskes på mobilen.
    • Store trykkflater: minst 44 × 44 px, og hele dagen er én knapp.
    • Trykk på en dag åpner et ark nederst med tre valg: Heldag (08–00), Formiddag (08–14) og Kveld (14–00). Opptatte perioder vises i husets farge og kan ikke velges.
    • Regelbrudd (kvote, helg, vindu) vises før man trykker «Book», og sjekkes uansett på nytt i Workeren.

    Senere idé, ikke med nå: passkeys (WebAuthn) som frivillig tillegg, slik at man kan logge inn med Face ID uten passord. Det kan legges til som et ekstra felt per bruker uten å endre resten av innloggingen.

    Worker-API

    Sidene og API-et ligger på samme adresse, så det trengs ingen CORS: Workeren sender ingen Access-Control-*-headere, og nettleseren lar ikke andre nettsider lese svarene. I wrangler.toml sendes bare /api/* til Worker-koden; alt annet er statiske filer.

    # HT14/badehusappen/wrangler.toml (utkast, ingen hemmeligheter)
name = "badehusappen"
main = "worker/index.js"
compatibility_date = "2026-10-25"
workers_dev = true

[assets]
directory = "./public"
run_worker_first = ["/api/*"]     # bare /api/ kjører Worker-koden

[[kv_namespaces]]
binding = "OKTER"
id = "<id fra wrangler kv namespace create>"
    // Enkel CSRF-sjekk i Workeren (utkast)
const APP_ORIGIN = "https://badehusappen.fluxreveal.workers.dev";
function erTrygg(req) {
  if (req.method === "GET" || req.method === "HEAD") return true;
  return req.headers.get("Origin") === APP_ORIGIN
      && (req.headers.get("Content-Type") || "").startsWith("application/json");
}   // ellers: 403

    Alle kall går til Workeren over HTTPS med JSON. Unntatt /api/login krever alle kall en gyldig økt-cookie (__Host-ht14_okt), se Økt-cookie. Nettleseren sender den automatisk, fordi kallene går til samme adresse.

    Regelmotor

    Regelmotoren er én ren funksjon uten sideeffekter, slik at nøyaktig samme kode kan kjøres i nettleseren (for å vise feilmelding tidlig) og i Workeren (som er den som bestemmer). Input er forespørselen, eksisterende bookinger, rules.json og «nå» i Europe/Oslo.

    Pseudokode

    function validateBooking(req, bookings, rules, now) {
  // now og alle datoer er i rules.timezone (Europe/Oslo)
  const today = localDate(now);
  if (!isDate(req.date) || !(req.period in rules.periods)) return fail("INVALID_INPUT");
  if (periodEnd(req.date, req.period) <= now)            return fail("IN_PAST");
  if (req.date > addMonths(today, rules.bookingWindow.months)) return fail("OUTSIDE_WINDOW"); // Å5
  if (overlapsActive(bookings, req.date, req.period))        return fail("SLOT_TAKEN");
  //   FULL overlapper AM og PM; AM og PM overlapper ikke hverandre
  if (req.override && req.actor.role === "admin")           return ok({ override: true });

  const daysBefore = diffDays(req.date, today);
  if (daysBefore < rules.liftSummerRulesWhenDaysBefore)
    return ok({ quota: rules.shortNoticeCountsTowardQuota });  // Å1

  const d = parse(req.date);
  if (!rules.summer.months.includes(d.month)) return ok({ quota: false }); // Å4
  const wd = weekday(d);                                       // "fri" | "sat" | "sun" | …
  if (!rules.summer.weekendDays.includes(wd))  return ok({ quota: false });

  // Kvotetellende = aktive bookinger + CANCELLED_LATE, med quota === true
  const mine = bookings.filter(b => b.household === req.household && countsForQuota(b));

  // 1) Maks 1 av hver ukedag per måned – teller DAGER (distinkte datoer)
  const sameWd = distinctDates(mine.filter(b => month(b.date) === d.month   // Å3: datoens måned
                                            && weekday(b.date) === wd));
  if (sameWd.length >= rules.summer.maxPerWeekdayPerMonth[wd]) return fail("QUOTA_WEEKDAY");

  // 2) Maks én helgedag per helg (fre–søn), også over månedsskifte (Å3)
  const wk = weekendKey(d);                                    // fredagens dato
  const sameWeekend = distinctDates(mine.filter(b => weekendKey(b.date) === wk
                                                  && b.date !== req.date));
  if (sameWeekend.length >= rules.summer.maxDaysPerWeekend) return fail("WEEKEND_LIMIT");

  return ok({ quota: true });
}

    Merk: en ny periode på en dato der husstanden allerede har en booking (f.eks. formiddag + ettermiddag samme fredag) teller ikke som en ny fredag, fordi det er dager som telles.

    Avbestilling

    function cancel(booking, actor, rules, now) {
  if (!["BOOKED"].includes(booking.status))       return fail("NOT_CANCELLABLE");
  if (!canCancel(actor, booking, rules))           return fail("FORBIDDEN");  // Å6
  const daysBefore = diffDays(booking.date, localDate(now));
  booking.status = daysBefore > rules.lateCancellationDays ? "CANCELLED"       // tidlig: ut av kvote
                                                            : "CANCELLED_LATE"; // sen: teller fortsatt
  booking.cancelledAt = now; booking.cancelledBy = actor.id;
  // bookingen beholdes i fila – ingenting slettes
}

    Statistikk

    Bruk måles i perioder: AM = 1, PM = 1, FULL = 2 (rules.periods[*].units). Tellingen gjøres for inneværende måned, inneværende sesong (jun–aug) og inneværende år, per husstand.

    Å7: COMPLETED og CHECKED_IN teller som bruk. NOT_CONFIRMED vises separat (ikke bruk før bekreftet). CANCELLED_LATE teller i kvote, ikke som bruk. Å2: spontan innsjekk teller i statistikken, men ikke i kvoten.

    Visningsstatus vs. lagret status

    Frontend og Worker beregner «hva er status nå» fra klokka. Eksempel: en CHECKED_IN formiddag vises som COMPLETED fra kl. 14:00 selv om den nattlige jobben ennå ikke har skrevet det til Git.

    function effectiveStatus(b, now) {
  if (periodEnd(b.date, b.period) > now) return b.status;
  if (b.status === "CHECKED_IN") return "COMPLETED";      // automatisk utsjekk
  if (b.status === "BOOKED")     return "NOT_CONFIRMED";  // ingen innsjekk
  return b.status;
}

    Samtidighet og optimistisk låsing

    To naboer kan trykke «Book» på samme lørdag i samme sekund. Git har ingen låser, men GitHub API krever at man sender med SHA-en til fila man endrer. Hvis fila er endret siden man leste den, avvises skrivingen – og Workeren leser på nytt og validerer igjen.

    async function commitWithRetry(path, mutate, maxTries = 3) {
  for (let i = 0; i < maxTries; i++) {
    const { json, sha } = await gh.read(path);         // innhold + sha
    const result = mutate(structuredClone(json));      // validering skjer her
    if (result.error) return result;                   // regelbrudd: ikke prøv igjen
    const res = await gh.write(path, result.json, sha);
    if (res.ok) return result;
    if (res.status !== 409) throw upstream(res);       // annen feil
    await sleep(150 * (i + 1));                        // kort pause og prøv igjen
  }
  return fail("CONFLICT_RETRY");
}
