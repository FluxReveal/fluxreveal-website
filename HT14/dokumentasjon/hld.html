    HLD – High Level Design

    Overordnet arkitektur for Badehus Booking System: hvilke deler løsningen består av, hvordan data flyter, og hvorfor den er bygget slik.

    v0.4 · 25.10.2026Teknisk valg (Thomas) – trenger ikke godkjenning

    Teknisk valg (Thomas) Arkitekturen på denne siden (GitHub Pages + én Cloudflare Worker + privat data-repo + GitHub Actions) er valgt av Thomas Gude Svensrud, som lager løsningen på oppdrag fra sameiet. Tekniske valg som dette trenger ikke godkjenning av sameiet. GitHub- og Cloudflare-kontoene eies av Thomas via FluxReveal-kontoene hans. Reglene løsningen håndhever er derimot bare forslag til sameiet ble enige om dem – se Bookingregler.

    Mål og føringer

    Ønsker fra start

    • GitHub Pages, GitHub Actions, HTML, CSS, JavaScript, JSON, CSV
    • Ingen database, ingen server
    • Ingen løpende kostnader
    • All historikk i Git, år for år
    • Alle data eksporterbare til CSV

    Kvalitetskrav

    • Responsiv: mobil og PC
    • Mulig å drifte for naboene uten utviklerkompetanse
    • Godt kommentert kode, lett å videreutvikle
    • Separasjon av regler, data og presentasjon
    • Regler i egen konfigurasjonsfil

    Den viktige begrensningen

    GitHub Pages alene kan ikke gi sikker innlogging eller skriving.

    • En skrivenøkkel i JavaScript er lesbar for alle som åpner siden.
    • En passordsjekk i JavaScript kan omgås.
    • Alt som publiseres på Pages er offentlig – selv fra et privat repo – og bookingdata er personopplysninger.

    Derfor anbefales ett lite, gratis «skrive- og innloggingsledd» mellom nettsiden og dataene: en Cloudflare Worker.

    Dataflyt

    Lesing og skriving

    Hvor bor hva?

    Offentlig (Pages)

    Kode for grensesnittet, stilark, ikoner. Ingen navn, ingen bookinger, ingen nøkler.

    Hemmelig (Worker-secrets)

    Fine-grained GitHub-token med tilgang kun til data-repoet, og nøkkel for signering av sesjonstoken.

    Privat (data-repo)

    Brukere (med passord-hash), bookinger, revisjonslogg, regler og CSV-arkiv.

    Tid og status

    • Status beregnes fra klokka i tidssonen Europe/Oslo når noe vises (f.eks. «pågår», «ferdig»).
    • GitHub Actions-cron kjører i UTC og kan bli forsinket. Den brukes derfor kun til å skrive endelig status i Git – ikke til å bestemme hva brukerne ser i øyeblikket.
    • Automatisk utsjekk ved periodens slutt: 08–14 → 14:00, 14–00 → 00:00.

    Forslag – ikke godkjent av sameiet 00:00 betyr slutten av dagen (24:00) i Europe/Oslo, inkludert sommertid. Se avklaring 10.

    Sikkerhet

    Trussel / behovTiltak i valgt arkitektur
    Uvedkommende leser bookingdataData ligger i privat repo; kun Workeren har token. Pages-output inneholder ingen data.
    Passord på avveieKun hash lagres (f.eks. PBKDF2 via WebCrypto). Ingen klartekstpassord i users.json.
    Manipulert klient omgår reglerAlle regler valideres server-side i Workeren mot rules.json.
    Stjålet innloggingKortlevd sesjonstoken.
    Dobbeltbooking ved samtidige forespørslerOptimistisk låsing via fil-SHA i GitHub API.
    Selvregistrering / ukjente brukereIngen selvregistrering. Administrator oppretter brukere og setter/resetter passord.
    Skjulte endringerHver endring er en commit, og logges i audit/<år>.jsonl med hvem, når, fra, til og kommentar. Alle adminhandlinger logges.
    Kall fra fremmede nettsiderWorkeren tillater kun origin https://fluxreveal.com (CORS), i tillegg til token-krav.
    Token med for vide rettigheterFine-grained token, lagret som Worker-secret (aldri i kode).

    Personvern

    • Bookingdata (navn, husstand, tidspunkt) er personopplysninger. De publiseres derfor ikke på GitHub Pages.
    • Innsyn: alle innloggede beboere kan se all historikk (krav om åpenhet).
    • Kravet «ingen data slettes permanent» står i spenning mot retten til sletting.

    Forslag – ikke godkjent av sameiet «Ingen sletting» gjelder bookinger. Utflyttede brukere deaktiveres og kan anonymiseres (navn → «Tidligere beboer Hus A»); husstanden beholdes. Se avklaring 9.

    Vurdert og forkastet

    100 % GitHub med Issues og konto per bruker

    Hver beboer måtte hatt egen GitHub-konto og brukt GitHub Issues. Forkastet: urealistisk for 20 ikke-tekniske naboer.

    Kun GitHub Pages med passord/nøkkel i JavaScript

    Forkastet fordi skrivenøkkel i JS er lesbar for alle, passordsjekk i JS kan omgås, og alt i Pages-output er offentlig.

    Risiko og avhengigheter

    • Avhengig av gratisplanene til GitHub og Cloudflare.
    • Actions-cron kan være forsinket (håndtert ved at status beregnes fra klokka).
    • Token i Worker må fornyes/roteres – se administratormanualen.
    • Reglene i rules.json er forslag til sameiet har godkjent dem (vedtektene § 10 og vedlegg 1) – se Hva må godkjennes?
