    1 Overordnet beskrivelse

    For alle naboene – uten teknikk. Hva er Badehusappen, hvorfor lager vi den, og hvordan blir det å bruke den?

    Hva er det?

    Badehusappen er en nettside som oppfører seg som en app, der vi i Halden Terrasse 14 kan se når badehuset er ledig, reservere det, avbestille og krysse av for at vi har brukt det. Den virker på mobil, nettbrett og PC. Du trenger ikke laste ned noe – du kan bare legge den på Hjem-skjermen på mobilen.

    I dag gjør vi det enkelt: vil du ha badehuset, sender du en e-post til en av naboene, og han svarer med en oversikt over de bookingene han vet om. Det har fungert fint takket være ham – men det blir mye e-post fram og tilbake, vi har ingen felles oversikt, og alt hviler på én person. Med Badehusappen ser alle den samme kalenderen, når som helst, og du kan booke selv.

    Slik er det i dag – og slik blir det

    ✉️ I dag

    • Du sender en e-post til en nabo og spør om dagen er ledig.
    • Han svarer med oversikten over det han vet om.
    • E-post fram og tilbake, og ingen felles oversikt.
    • Alt avhenger av at én person har tid og husker alt.

    📱 Med Badehusappen

    • Du åpner Badehusappen på mobilen.
    • Alle ser den samme kalenderen, med husets farge på hver dag.
    • Du booker selv, og reglene sjekkes med en gang.
    • Ingen trenger å sitte med oversikten alene.

    📅 Én felles kalender

    Laget for mobilen: du ser én uke om gangen og trykker på en dag for å booke. Hele måneden kan også vises. Hvert hus har sin farge, så du ser med en gang hvem som har badehuset.

    ⚖️ Rettferdige regler

    Om sommeren passer Badehusappen på at fredager, lørdager og søndager fordeles mellom husene.

    🔍 Åpent for alle

    Alle kan se historikk og statistikk. Ingenting forsvinner i det stille.

    Hvorfor?

    • Flere kan bruke det: Vi har stort sett tatt badehuset hele dager. Nå kan du også ta bare en del av dagen – formiddag, ettermiddag eller kveld – så noen andre kan bruke resten.
    • Rettferdig fordeling av de mest populære sommerdagene.
    • Åpenhet: Det skal være lett å se hvordan badehuset blir brukt – uten rangering og uten pekefinger.
    • Enkel og gratis: Hvem som helst av oss skal kunne passe på Badehusappen uten å være utvikler, og den skal ikke koste noe.
    • God dokumentasjon, så andre enn Thomas kan ta over hvis det trengs.

    Hvem bruker Badehusappen?

    Vanlig bruker kan

    • logge inn (og holde seg innlogget på mobilen)
    • se kalender
    • opprette booking
    • avbestille booking
    • sjekke inn
    • bekrefte at reservasjonen ble brukt
    • se all historikk
    • se statistikk

    Kan ikke: endre regler, opprette brukere eller overstyre begrensninger.

    Administrator kan i tillegg

    • opprette og deaktivere brukere
    • tilbakestille passord
    • logge ut en mistet mobil
    • endre regler
    • overstyre begrensninger
    • korrigere historikk
    • importere og eksportere data

    Alt administratorene gjør, blir logget.

    Slik fungerer det i hverdagen

    Dagen er delt i tre

    Badehuset åpner kl. 10, og dagen er delt i tre perioder. Du booker én eller flere av dem. Heldag betyr alle tre, og det er det som er forhåndsvalgt. Inndelingen er en del av forslaget vi tar på sameiemøtet.

    En måned i kalenderen

    Fire hverdagssituasjoner

    «Vi vil ha badehuset lørdag om tre uker»

    Åpne kalenderen, trykk på lørdagen – Heldag er allerede valgt. Badehusappen sjekker sommerreglene og bekrefter. Dagen får husets farge.

    «Badehuset er ledig nå – vi går ned!»

    Er det ledig, kan du bare sjekke inn – uten å ha reservert. Velg hvor lenge dere blir (til kl. 14, 17 eller 24), så noteres det hvem som er der.

    «Vi rakk ikke å sjekke inn»

    Ikke noe problem. Bookingen står som «ikke bekreftet», og du kan trykke «Vi brukte badehuset» etterpå.

    «Planene endret seg»

    Avbestill i Badehusappen – hele dagen eller bare én periode. Mer enn 7 dager før: dagen teller ikke lenger i sommerkvoten. 7 dager eller mindre før: dagen blir ledig for de andre, men teller fortsatt i kvoten.

    De viktigste reglene – kort fortalt

    Dette er Thomas sitt forslag til regler. Vi bestemmer dem sammen på sameiemøtet.

    RegelKort forklart
    BookingvinduDu kan booke maks 3 måneder frem i tid.
    Sommerkvote (juni, juli, august)Hvert hus kan ha maks 1 fredag, 1 lørdag og 1 søndag per måned. Det er dagen som teller – en halv fredag er også «en fredag».
    Helgebegrensning (sommer)Maks én helgedag per helg per hus (ikke fre+lør, lør+søn eller fre+søn samme helg).
    7-dagersregelEr det mindre enn 7 dager til datoen, gjelder ikke sommerbegrensningene – da er det førstemann til mølla.
    AvbestillingTidlig (mer enn 7 dager før) eller sen (7 dager eller mindre før) – se Regler.

    Alle detaljer og eksempler står på siden Bookingregler.

    Statistikk uten rangering

    Statistikken viser hvor mye hvert hus har brukt badehuset denne måneden, denne sommeren (juni–august) og i år. Bruk måles i perioder: formiddag, ettermiddag og kveld = 1 hver, heldag = 3. Det er for åpenhetens skyld – ikke en konkurranse.

    Ikke bekreftede bookinger vises for seg (regnes ikke som bruk før de er bekreftet), og sent avbestilte teller i kvoten, men ikke som bruk. Se avklaring 7 i Bookingreglene.

    Trygghet og personvern

    • Man registrerer seg ikke selv – en administrator lager brukeren med e-postadressen din og et startpassord. Første gang velger du ditt eget passord.
    • Du logger inn med e-post og passord, og mobilen kan huske passordet og fylle det inn med Face ID eller fingeravtrykk. Du holder deg innlogget i omtrent ett år.
    • Mister du mobilen, kan en administrator logge den ut. Etter flere feil passord på rad blir det en kort pause, så ingen kan gjette seg inn.
    • Bookingdata er personopplysninger og skal derfor ikke ligge åpent på internett. Badehusappen, slik Thomas har valgt å bygge den, lagrer dataene i et privat lager (se HLD).
    • Passord lagres aldri i klartekst.
    • Ingen bookinger slettes, og alle endringer kan spores.

    Når noen flytter, deaktiveres brukeren og kan anonymiseres (f.eks. navnet byttes til «Tidligere beboer Hus A»), mens husstanden beholdes i historikken. Se avklaring 9.

    Hva er ikke med i starten?

    • Ingen varsler på e-post eller SMS – det kan komme senere.
    • Innlogging helt uten passord (passkeys med Face ID) er en idé for senere.
    • Vedtektene for sameiet er under arbeid. Thomas har laget et forslag til § 10 og vedlegg 1 om badehuset, som sameiet skal ta stilling til.

    Den viktige begrensningen

    GitHub Pages alene kan ikke gi sikker innlogging eller skriving.

    • En skrivenøkkel i JavaScript er lesbar for alle som åpner siden.
    • En passordsjekk i JavaScript kan omgås.
    • Alt som publiseres på Pages er offentlig – selv fra et privat repo – og bookingdata er personopplysninger.

    Derfor ligger Badehusappen i en liten, gratis Cloudflare Worker: den serverer selve sidene og står for innlogging og skriving. GitHub Pages brukes fortsatt til startsiden og dokumentasjonen på fluxreveal.com/HT14/.

    Dataflyt

    Lesing og skriving

    Hvor bor hva?

    Offentlig (kode og sider)

    Kode for grensesnittet, stilark, ikoner, startsiden og dokumentasjonen. Ingen navn, ingen bookinger, ingen nøkler.

    Hemmelig (Worker-secrets)

    Fine-grained GitHub-token med tilgang kun til data-repoet, og en hemmelig «pepper» som blandes inn i hashen av økt-nøkler.

    Privat (data-repo)

    Brukere (med passord-hash), bookinger, revisjonslogg, regler og CSV-arkiv.

    Innlogging og økter

    Badehusappen har sin egen innlogging med e-post og passord, og det er Workeren som sjekker passordet. Passordene lagres aldri i klartekst – bare som PBKDF2-hash i users.json i det private data-repoet. Målet er at man logger inn én gang på mobilen og så slipper å tenke mer på det.

    🔑 Laget for passordhåndtering

    Innloggingsskjemaet bruker autocomplete="username" og autocomplete="current-password" (og new-password når man velger passord). Da tilbyr iPhone og Android å lagre passordet, og fyller det inn med Face ID eller fingeravtrykk neste gang.

    📱 Innlogget i et år

    Etter innlogging får mobilen en trygg informasjonskapsel (cookie) som varer i ca. 365 dager. Fristen fornyes når man bruker Badehusappen, så den som bruker den jevnlig, blir aldri logget ut.

    🛡️ Kontroll for admin

    Workeren har en liste over aktive økter. En administrator kan logge ut én mistet mobil, eller alle økter for en bruker. Etter flere feil passord i strekk blir det en kort pause.

    Hvorfor ikke Cloudflare Access?

    Cloudflare Access ble vurdert, men valgt bort av Thomas. En Access-innlogging varer maks 30 dager, og man logger inn med en engangskode på e-post. En slik kode kan ikke lagres på mobilen, så man må hente en ny kode fra e-posten hver gang økten går ut. Med egen innlogging kan mobilen huske passordet, og man er innlogget i et helt år.

    Badehusappen på mobilen

    • Hjem-skjerm (PWA): Badehusappen har et web app-manifest og et ikon på sin egen adresse (badehusappen.fluxreveal.workers.dev). Velger man «Legg til på Hjem-skjerm», åpner den rett i kalenderen (start_url er kalenderen, display: standalone) – uten adressefelt, som en vanlig app. På iPhone har Hjem-skjerm-appen sine egne cookies; er man logget inn i Safari når man legger den til, blir innloggingen med (iOS 17.2 og nyere). Ellers logger man inn én gang i appen.
    • Rett til kalenderen: Er man allerede innlogget, hopper Badehusappen over innloggingen og viser kalenderen med en gang.
    • Mobil først: Ukevisning er standard, med store trykkflater. Hver dag viser tre rader (formiddag 10–14, ettermiddag 14–17, kveld 17–24). Trykk på en dag eller en ledig rad for å booke én eller flere perioder – heldag er forhåndsvalgt. Månedsvisning kan velges.
    • Senere idé: passkeys, slik at de som vil, kan logge inn med Face ID helt uten passord. Det er ikke med nå.

    Tid og status

    • Status beregnes fra klokka i tidssonen Europe/Oslo når noe vises (f.eks. «pågår», «ferdig»).
    • GitHub Actions-cron kan bli forsinket. Den brukes derfor kun til å skrive endelig status i Git – ikke til å bestemme hva brukerne ser i øyeblikket.
    • Automatisk utsjekk ved hver periodes slutt: formiddag kl. 14:00, ettermiddag kl. 17:00, kveld kl. 24:00 (00:00).
    • Hver periode lagres som sin egen booking. En heldag er tre bookinger med felles groupId, så de kan avbestilles og sjekkes ut hver for seg.

    00:00 betyr slutten av dagen (24:00) i Europe/Oslo, inkludert sommertid. Se avklaring 10 i Bookingreglene.

    Sikkerhet

    Trussel / behovTiltak i valgt arkitektur
    Uvedkommende leser bookingdataData ligger i privat repo; kun Workeren har token. De statiske sidene inneholder ingen data.
    Passord på avveieKun hash lagres (PBKDF2 via WebCrypto, med salt). Ingen klartekstpassord i users.json.
    Gjetting av passordBegrensning på antall forsøk: etter flere feil passord i strekk blir e-postadressen (og IP-adressen) midlertidig stengt i noen minutter, og pausen øker ved flere feil.
    Manipulert klient omgår reglerAlle regler valideres server-side i Workeren mot rules.json.
    Stjålet eller mistet mobilØkten ligger i en HttpOnly-cookie (kan ikke leses av JavaScript), Secure (bare HTTPS) og SameSite=Lax. Hver økt står i øktlisten, så en administrator kan logge ut én mobil eller alle økter for en bruker. Bytte av passord logger ut alle andre økter.
    Innlogging fra andre nettsider (CSRF)SameSite=Lax-cookie (sendes ikke med skjema eller kall fra andre nettsider), og Workeren godtar bare endringer når Origin er Badehusappens egen adresse og innholdet er JSON.
    Dobbeltbooking ved samtidige forespørslerOptimistisk låsing via fil-SHA i GitHub API.
    Selvregistrering / ukjente brukereIngen selvregistrering. Administrator oppretter brukere og setter/resetter passord.
    Skjulte endringerHver endring er en commit, og logges i audit/<år>.jsonl med hvem, når, fra, til og kommentar. Alle adminhandlinger logges.
    Kall fra fremmede nettsiderSidene og API-et har samme adresse, så Workeren sender ingen CORS-headere. Nettleseren lar derfor ikke andre nettsider lese svarene, og alle kall krever gyldig økt.
    Token med for vide rettigheterFine-grained token, lagret som Worker-secret (aldri i kode).

    Personvern

    • Bookingdata (navn, husstand, tidspunkt) er personopplysninger. De ligger derfor aldri i de offentlige filene, verken på GitHub Pages eller blant Workerens statiske filer.
    • Innsyn: alle innloggede beboere kan se all historikk (krav om åpenhet).
    • Kravet «ingen data slettes permanent» står i spenning mot retten til sletting.

    «Ingen sletting» gjelder bookinger. Utflyttede brukere deaktiveres og kan anonymiseres (navn → «Tidligere beboer Hus A»); husstanden beholdes. Se avklaring 9.

    Vurdert og forkastet

    100 % GitHub med Issues og konto per bruker

    Hver beboer måtte hatt egen GitHub-konto og brukt GitHub Issues. Forkastet: urealistisk for 20 ikke-tekniske naboer.

    Kun GitHub Pages med passord/nøkkel i JavaScript

    Forkastet fordi skrivenøkkel i JS er lesbar for alle, passordsjekk i JS kan omgås, og alt i Pages-output er offentlig.

    Sidene på fluxreveal.com, bare API-et på workers.dev

    Forkastet fordi innloggings-cookien da blir en tredjeparts-cookie, og Safari på iPhone blokkerer slike som standard. Å flytte DNS for fluxreveal.com til Cloudflare (for et eget api-underdomene) ble også valgt bort.

    Cloudflare Access foran Badehusappen

    Forkastet fordi en Access-økt varer maks 30 dager og bruker engangskoder på e-post, som ikke kan lagres på mobilen. Det blir for mye styr for naboene.

    Risiko og avhengigheter

    • Avhengig av gratisplanene til GitHub og Cloudflare. Endrer Cloudflare vilkårene, kan Workeren flyttes; dataene ligger i Git.
    • Actions-cron kan være forsinket (håndtert ved at status beregnes fra klokka).
    • Token i Worker må fornyes/roteres – se administratormanualen.
    • Reglene i rules.json er forslag til vi har bestemt dem på sameiemøtet (vedtektene § 10 og vedlegg 1) – se Forslag til vedtekter.

    Hvorfor det virker: sidene og /api/ ligger på samme adresse (https://badehusappen.fluxreveal.workers.dev), så cookien er en vanlig førsteparts-cookie og Safari på iPhone sender den uten problemer. workers.dev står på Public Suffix List, så cookien deles ikke med andre workers.dev-adresser. Frontend kaller med relative adresser (fetch("/api/me")), og nettleserens standard credentials: "same-origin" holder.

    Hvorfor Lax og ikke Strict: Når man åpner en Hjem-skjerm-app på iPhone eller følger lenken fra fluxreveal.com/HT14/, kan første forespørsel regnes som en navigasjon fra et annet sted. En Strict-cookie blir da ikke sendt med den første forespørselen, mens Lax blir det. Siden Badehusappen sjekker innloggingen med GET /api/me etter at siden er lastet, ville Strict sannsynligvis også gått, men Lax er det trygge valget. CSRF-vernet ivaretas av Lax (ingen cookie på POST fra andre nettsider) pluss Origin-sjekken i Workeren.

    Hjem-skjerm på iPhone: En Hjem-skjerm-app har sine egne cookies, adskilt fra Safari. Fra iOS 17.2 kopieres Safari-cookiene inn når man trykker «Legg til på Hjem-skjerm», så den som er logget inn i Safari, er også logget inn i appen. Ellers logger man inn én gang i appen; passordet fylles inn automatisk.

    Regelmotor

    Regelmotoren er én ren funksjon uten sideeffekter, slik at nøyaktig samme kode kan kjøres i nettleseren (for å vise feilmelding tidlig) og i Workeren (som er den som bestemmer). Input er forespørselen, eksisterende bookinger, rules.json og «nå» i Europe/Oslo.

    Pseudokode

    function validateBooking(req, bookings, rules, now) {
  // now og alle datoer er i rules.timezone (Europe/Oslo)
  const today = localDate(now);
  if (!isDate(req.date) || !(req.period in rules.periods)) return fail("INVALID_INPUT");
  if (periodEnd(req.date, req.period) <= now)            return fail("IN_PAST");
  if (periodStart(req.date, req.period) <= now)          return fail("STARTED");     // da: «Sjekk inn nå»
  if (req.date > addMonths(today, rules.bookingWindow.months)) return fail("OUTSIDE_WINDOW"); // Å5
  if (overlapsActive(bookings, req.date, req.period))        return fail("SLOT_TAKEN");
  //   de tre periodene AM / MID / PM overlapper ikke hverandre
  if (req.override && req.actor.role === "admin")           return ok({ override: true });

  const daysBefore = diffDays(req.date, today);
  if (daysBefore < rules.liftSummerRulesWhenDaysBefore)
    return ok({ quota: rules.shortNoticeCountsTowardQuota });  // Å1

  const d = parse(req.date);
  if (!rules.summer.months.includes(d.month)) return ok({ quota: false }); // Å4
  const wd = weekday(d);                                       // "fri" | "sat" | "sun" | …
  if (!rules.summer.weekendDays.includes(wd))  return ok({ quota: false });

  // Kvotetellende = aktive bookinger + CANCELLED_LATE, med quota === true
  const mine = bookings.filter(b => b.household === req.household && countsForQuota(b));

  // 1) Maks 1 av hver ukedag per måned – teller DAGER (distinkte datoer)
  const sameWd = distinctDates(mine.filter(b => month(b.date) === d.month   // Å3: datoens måned
                                            && weekday(b.date) === wd));
  if (sameWd.length >= rules.summer.maxPerWeekdayPerMonth[wd]) return fail("QUOTA_WEEKDAY");

  // 2) Maks én helgedag per helg (fre–søn), også over månedsskifte (Å3)
  const wk = weekendKey(d);                                    // fredagens dato
  const sameWeekend = distinctDates(mine.filter(b => weekendKey(b.date) === wk
                                                  && b.date !== req.date));
  if (sameWeekend.length >= rules.summer.maxDaysPerWeekend) return fail("WEEKEND_LIMIT");

  return ok({ quota: true });
}

    Merk: en ny periode på en dato der husstanden allerede har en booking (f.eks. formiddag + ettermiddag samme fredag) teller ikke som en ny fredag, fordi det er dager som telles.

    Flere perioder i én forespørsel sjekkes med validateBookingMulti: periodene sorteres, heldag (alle tre) avvises med FULLDAY_STARTED hvis kl. 10 har passert samme dag, og så sjekkes hver periode med validateBooking mot eksisterende bookinger pluss de andre periodene i samme forespørsel. Feiler én, lagres ingen.

    function validateBookingMulti(req, bookings, rules, now) {
  const periods = sortByStart(unique(req.periods));            // f.eks. ["AM","MID","PM"]
  if (!periods.length) return fail("NO_PERIOD");
  if (isFullDay(periods) && periodStart(req.date, "AM") <= now) return fail("FULLDAY_STARTED");
  const tmp = [...bookings];
  for (const p of periods) {
    const r = validateBooking({ ...req, period: p }, tmp, rules, now);
    if (!r.ok) return r;                                       // alt eller ingenting
    tmp.push({ date: req.date, period: p, household: req.household, status: "BOOKED", quota: r.quota });
  }
  return ok({ periods, quota: r.quota });
}

    function cancel(booking, actor, rules, now) {
  if (!["BOOKED"].includes(booking.status))       return fail("NOT_CANCELLABLE");
  if (!canCancel(actor, booking, rules))           return fail("FORBIDDEN");  // Å6
  const daysBefore = diffDays(booking.date, localDate(now));
  booking.status = daysBefore > rules.lateCancellationDays ? "CANCELLED"       // tidlig: ut av kvote
                                                            : "CANCELLED_LATE"; // sen: teller fortsatt
  booking.cancelledAt = now; booking.cancelledBy = actor.id;
  // bookingen beholdes i fila – ingenting slettes
}

    Statistikk

    Bruk måles i perioder: AM, MID og PM = 1 hver, så en heldag = 3 (rules.periods[*].units). Tellingen gjøres for inneværende måned, inneværende sesong (jun–aug) og inneværende år, per husstand.

    Å7: COMPLETED og CHECKED_IN teller som bruk. NOT_CONFIRMED vises separat (ikke bruk før bekreftet). CANCELLED_LATE teller i kvote, ikke som bruk. Å2: spontan innsjekk teller i statistikken, men ikke i kvoten.

    function effectiveStatus(b, now) {
  if (periodEnd(b.date, b.period) > now) return b.status;
  if (b.status === "CHECKED_IN") return "COMPLETED";      // automatisk utsjekk
  if (b.status === "BOOKED")     return "NOT_CONFIRMED";  // ingen innsjekk
  return b.status;
}

    Samtidighet og optimistisk låsing

    To naboer kan trykke «Book» på samme lørdag i samme sekund. Git har ingen låser, men GitHub API krever at man sender med SHA-en til fila man endrer. Hvis fila er endret siden man leste den, avvises skrivingen – og Workeren leser på nytt og validerer igjen.

    async function commitWithRetry(path, mutate, maxTries = 3) {
  for (let i = 0; i < maxTries; i++) {
    const { json, sha } = await gh.read(path);         // innhold + sha
    const result = mutate(structuredClone(json));      // validering skjer her
    if (result.error) return result;                   // regelbrudd: ikke prøv igjen
    const res = await gh.write(path, result.json, sha);
    if (res.ok) return result;
    if (res.status !== 409) throw upstream(res);       // annen feil
    await sleep(150 * (i + 1));                        // kort pause og prøv igjen
  }
  return fail("CONFLICT_RETRY");
}
